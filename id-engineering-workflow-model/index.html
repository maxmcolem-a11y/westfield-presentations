Premise

Core Premise

The work is not Trello cleanup. The work is defining how product work moves.

Industrial Design is maturing its Trello system into a clearer product-development workflow. Trello is the current tool, but the operating model is ownership, action, blockers, handoff readiness, and decision data.

Movement

How design and engineering work moves.

Ownership

Who owns the work at each point.

Blockers

What prevents the work from moving.

Evidence

What proves the stage is complete.

Physical Workflow

Workflow Before Tool

Start with the physical workflow model.

If every project were a paper brief in a folder, the basic questions are simple. Those questions become the card standards, list meanings, and handoff rules.

Who has the folder right now?

Current ownership is explicit.

What action are they responsible for?

The next required action is visible.

What information do they need?

Inputs, files, samples, decisions, or blockers are named.

Where does the folder go next?

Handoff destination and readiness are clear.

What proves completion?

The output or decision is attached, linked, or recorded.

Executive Summary

Operating Goal

Industrial Design and Engineering need a simple card-based workflow.

The goal is active product work that is visible, ownership that is clear, blockers that are explicit, and improvement based on real workflow data.

Make work visible

The board can be read without reconstructing status from memory.

Clarify ownership

Every active card has a current owner or owner group.

Improve handoffs

Cards move with source files, decisions, blockers, and completion criteria.

Support flexibility

The process helps the team pivot without treating every pivot as a failure.

Why This Matters

Cross-Functional Pressure

Physical product work has too many dependencies to run on informal status memory.

One product can involve concept direction, CAD, renderings, physical samples, factory feedback, testing, sourcing, cost targets, packaging, retailer requirements, leadership decisions, and line-review deadlines.

Informal priority

Priorities are visible to some people but not everyone.

Implied ownership

People infer responsibility instead of seeing it.

Late blockers

Missing inputs and decisions surface too late.

Reconstructed reporting

Weekly reporting requires rebuilding status manually.

Agent limits

AI agents can help only if the board itself is consistent.

Execution Questions

Reliable Operating Surface

Cards need to answer basic execution questions.

A reliable operating surface makes the next action, blocker, decision, file, sample, test, approval, and stage definition visible.

What is this work?

Project or task title plus business reason.

Who owns it now?

Current owner or owner group.

What is next?

Next action, required input, blocker, or decision needed.

What does done mean?

Definition of done for the current stage.

Agile-Informed

Not Agile Theater

Use Agile ideas only where they improve physical product work.

The model borrows useful habits without forcing software rituals onto hardware, samples, factories, cost feedback, retailer needs, and leadership decisions.

Useful here

  • Visible work
  • Smaller pieces when helpful
  • Frequent review
  • Blocker surfacing
  • WIP discipline
  • Retrospectives from real friction

Not the starting point

  • Strict two-week commitments for all work
  • Story points as primary system
  • Mandatory daily standups
  • Scrum Master role
  • Mismatched product owner structure
  • Custom fields nobody uses

Data Discipline

Useful Data, Not Decorative Data

The workflow needs data that answers operating questions.

Recent S28 cleanup showed the risk: unused, inconsistent, or repetitive fields become noise. Useful data helps leaders and teams see friction, readiness, expensive execution, and decision points.

Where is work stuck?

Lists, blockers, and comments make waiting visible.

Which handoffs create rework?

Handoff notes and retrospectives expose repeated friction.

Which work is ready?

Ready cards have inputs and completion criteria.

Which work is costly now?

Cards show engineering, sample, CAD, factory, or tooling effort.

Visible Data

Board Data Model

Favor visible workflow data over custom fields.

Custom fields are useful only when they carry structured information that is actively reviewed and cannot be represented more clearly by the board workflow.

Lists

State and ownership.

Labels

Categories, channels, brands, and useful filters.

Attachments

Source documents, SharePoint links, sample photos, CAD, specs, and references.

Comments

Decisions, blockers, handoff notes, and context.

Checklists

Stage-specific tasks and completion rules.

Linked cards

Cross-board visibility and related work.

12 / 22
WIP Discipline

Exploration vs. Execution

Kill weak ideas early. Once costly execution starts, finish the current stage or make an explicit kill decision.

Early concepting can die quickly. Once engineering time, technical packs, CAD, tooling direction, sample work, or factory effort has been invested, the workflow needs a clear finish-or-stop decision.

Sample Evidence

Physical Product Reality

A sample is not only an expense. It is evidence.

A sample can prove cost, reveal overbuild or underbuild, support value engineering, support retailer feedback, or show leadership why an idea cannot meet the requested target.

Cost proof

Real sample data beats abstract debate.

Construction proof

Overbuild, underbuild, and assembly issues become visible.

Decision proof

Leadership sees what can or cannot meet target.

Sometimes the faster and cheaper path is to build one sample, create the first bill of materials, then value engineer from something real.

Stage 1 Model

Core Practices

Stage 1 stays focused and practical.

The goal is to improve team-level workflow without creating a large company process initiative.

Define real workflow

Finalize board mechanics only after real work states are clear.

Use Trello as operating surface

Keep cards readable to humans and AI agents.

Require next actions

Active cards must show the next action or blocker.

Make blockers explicit

Blocked cards name the blocker and needed input.

Review active and blocked work

Use reviews to move work, not perform process theater.

Turn retrospectives into changes

Outcomes become board changes, card standards, or follow-up cards.

15 / 22
Board Flow + Card Standards

Ready, Active, Blocked, Review, Done

List names should describe real work states.

A card in Ready has enough information to begin. A card in Blocked names the blocker. A card in Review or Handoff includes the output, decision, or next owner.

Suggested flow

Intake / Ideas, Needs Definition, Ready, In Progress, Blocked, Review / Approval, Sample / Test / Vendor Follow-Up, Handoff to Next Team, Done / Archived.

Active card standard

Title, business reason, owner, status, next action, blocker, date or handoff point, relevant files, and definition of done.

Engineering handoff standard

Target cost, channel context, requirements, dimensions, material direction, sample state, testing needs, CAD/reference files, open questions, critical path, and rough calendar-day expectation when engineering effort is substantial.

16 / 22
Retrospectives

Meaningful Milestones

Retrospectives happen at real workflow handoffs, not arbitrary calendar intervals.

When a project finishes with one team and hands off to another, the team that just held the work does a short retrospective focused on that stage.

Inputs

Card comments, blockers, missing information, rework, decisions, and agent summaries.

Questions

What slowed this stage down? What was missing? Where did we wait? What caused rework? Which handoff was unclear?

Outputs

One to three concrete changes: board rule, card standard, checklist, or follow-up card.

Agent support

The agent summarizes card history before the retrospective; humans add judgment.

SAFe Compatibility

Future Compatibility, Not Current Adoption

This is not SAFe adoption, but it builds habits that would matter later.

Stage 1 does not require PI planning, release trains, formal SAFe roles, or story-point estimation. It builds visible team work systems, ownership, WIP limits, blocker visibility, definitions of ready and done, retrospectives, and better operating data.

Local rule

Do not force story points or quarterly loading into ID + Engineering workflow.

Future rule

If Westfield and HengFeng later adopt a company-wide SAFe direction, estimation and capacity planning belong in that larger system.

Practical bridge

Better team workflow data makes broader planning more credible if the company needs it.

Success Criteria

What Success Looks Like

Success is a board that makes work clearer and decisions better.

Stage 1 succeeds if active ID work is easier to understand, Engineering can see ready/blocked/review states, blockers are named earlier, handoffs require less reconstruction, retrospectives improve the process, and AI summaries become more reliable.

Active work clarity

The board shows current owner, next action, blocker, and completion criteria.

Less meeting reconstruction

Handoffs and reports read from the card record.

Better workflow data

The team can see where work slows down and why.

Agent-ready reporting

AI summaries become more reliable because the board is consistent.

External Validation

Industry Reference Points

The argument does not depend on jargon.

Agile, Lean, Kanban, Six Sigma, and SAFe all point toward the same practical lesson when used well: understand the real work, make it visible, measure the right friction, and improve based on evidence.

Kanban / Scrumban

Visualize work, limit WIP, and improve flow.

Agile for hardware

Use modified Agile practices for hardware-specific constraints.

SAFe for Hardware

Lean-Agile can scale into hardware contexts, but only when the organization chooses that broader model.

Practical conclusion

Start with the team and the physical product-development process.
